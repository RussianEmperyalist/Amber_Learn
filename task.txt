Стек: vanilla HTML/CSS/JS (ES-модули), оффлайн-PWA, хранение в IndexedDB, без бэкенда. Зависимости в рантайм не добавлять.
Для dev-тестов разрешён только Playwright. Язык интерфейса и контента — русский.

ОБЩИЕ ПРАВИЛА
- Не переписывай теорию, hook, recap, quiz и тексты уроков. Меняй только то, что указано ниже.

ЭТАП 1. ПЕСОЧНИЦА scripts/js-runner.js (критично)
Проблема: сообщение `done` отправляется сразу после запуска пользовательского кода. Вывод из .then, после await и из setTimeout теряется,
поэтому задания уроков 23, 24, 25 и часть 27 не проходятся. Кроме того, ошибки внутри async-обёртки не попадают в stderr,
`done` может уйти дважды, а переменные let/const недоступны через `for (k in window)`.
Сделай:
1. Запускай код внутри async-функции и дожидайся её завершения (await промиса).
2. Затем дожидайся «тишины». Нужно отслеживать активные таймеры (обернуть setTimeout/setInterval) и подождать, пока очередь
   пуста, но не дольше общего таймаута 5 с. Зависший промис без таймеров не должен вешать запуск: после опустошения
   микрозадач и таймеров завершай.
3. Ловить синхронные ошибки, отклонённые промисы (unhandledrejection) и window.onerror, и писать их в stderr в виде "Error: сообщение".
4. `done` отправляй ровно один раз (флаг).
5. Замени сбор переменных через window на «пробу». Сигнатура: runJS(code, { probe: ['x', 'total'] }).
   После пользовательского кода внутри той же функции добавь для каждого имени:
   try { __vars.x = typeof x !== 'undefined' ? x : undefined } catch(e) {}.
   Значения возвращай в сериализуемом виде (примитивы как есть, объекты и массивы через JSON.stringify).
6. console.log должен форматировать: объекты и массивы через JSON.stringify, undefined и null как строки, ошибки как "Error: msg".
7. Поддержи необязательное поле задания `fixture` (строка HTML). Она вставляется в document.body песочницы перед запуском кода.
   Для уроков 26–28 и 30 проверь, где в условии написано «элемент уже есть», и добавь fixture там, где его не хватает.
8. Экранируй `</script>` в коде, как сейчас. Проверь, что код с обратными кавычками и `${}` не ломает srcdoc.

ЭТАП 2. ПРОВЕРКИ scripts/editor.js
Баги:
- В has-call в строке-шаблоне стоит `\s`, нужно `\\s`. Сейчас регулярка выглядит как `имяs\(` и почти всегда не срабатывает.
  Имя функции экранируй через escapeRegExp.
- `check.equals || check.value` превращает 0 и '' в пустую строку. Используй `??`.
- Проверка `stdout` сейчас работает как «содержит». Это позволяет пройти задание через console.log("5").
Новые виды проверок (старые оставить):
- stdout-exact: trim() всего вывода строго равен значению (опционально с нормализацией \r\n).
- stdout-lines: массив ожидаемых строк, порядок строгий.
- code-has: regex по ИСХОДНОМУ коду без комментариев и без содержимого строк. Пример: {kind:"code-has", pattern:"\\bconst\\s+name\\b"}.
- code-not: regex, которого в коде быть не должно. Пример: запрет литерала "Amber" в console.log, если значение должно идти из переменной.
- var: сравнение значения из пробы (см. этап 1).
- has-call, has-template-literal (поправить: бэктики с ${} многострочно), no-error.
- Неизвестный kind теперь считается ОШИБКОЙ (в консоль и в UI), а не молчаливым проходом.
При провале показывай студенту, какая именно проверка не прошла, человеческой фразой. Для этого добавь необязательное поле `message` в check
и выводи его. Например: «Объяви переменную через const».
